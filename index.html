From Wallet Seed to Ethereum Address

Hashing, key derivation and cryptographic primitives in the Ethereum wallet pipeline (Homework 2). Each step uses a different tool because each step solves a different problem.

1. The pipeline

  1. Mnemonic (12–24 words)Human-readable encoding of random entropy plus a checksum.
  2. BIP-39: PBKDF2-HMAC-SHA512, 2048 roundsSeed 512 bits
  3. BIP-32 + BIP-44: HMAC-SHA512 chain, path m/44'/60'/0'/0/0Private key 256 bits
  4. secp256k1: scalar multiplication K = k·GPublic key 64 bytes (x ‖ y)
  5. Keccak-256 of the 64 bytes, keep the last 20 bytesAddress 160 bits = 40 hex characters

2. The primitives, one by one

BIP-39: mnemonic and seed encoding + derivation

Fresh random entropy (128 to 256 bits) gets a short checksum (entropy length ÷ 32 bits) appended, and the result is cut into 11-bit groups. Each group indexes a 2048-word list. 128 + 4 = 132 bits = 12 words; 256 + 8 = 264 bits = 24 words. The seed is then derived with PBKDF2-HMAC-SHA512, 2048 iterations, using the string "mnemonic" plus an optional passphrase as salt. The passphrase ("25th word") produces a completely different wallet from the same words.

BIP-32: hierarchical deterministic keys derivation

The seed goes through HMAC-SHA512 with the key "Bitcoin seed". The left 256 bits become the master private key, the right 256 bits the chain code. Each child key is computed from the parent key, the parent chain code and an index. Indexes from 231 up are hardened (shown with ') and use the private key, so a leaked child public key plus chain code cannot reveal the parent private key. One seed therefore yields a whole tree of keys.

BIP-44: standard paths convention

Fixes the tree layout: m / 44' / coin_type' / account' / change / address_index. Ethereum uses coin type 60, so the first account is m/44'/60'/0'/0/0, the second …/0/1. Ethereum has no separate change addresses, so the change level stays 0. A shared convention lets different wallets restore the same addresses from the same mnemonic.

secp256k1: public-key cryptography asymmetric

An elliptic curve y² = x³ + 7 over the prime field p = 2256 − 232 − 977, with a generator point G of prime order n ≈ 2256. A private key is an integer k in [1, n−1]; the public key is K = k·G. Computing K from k is fast, but recovering k from K is the elliptic-curve discrete logarithm problem, which is infeasible at this size. The same relationship lets the owner sign transactions with ECDSA so anyone can verify the signature using only the public key.

Keccak-256: hashing one-way

Takes the 64-byte public key (x and y, without the 0x04 prefix) and compresses it into 32 bytes. Ethereum keeps the last 20 bytes as the address. Hashing is one-way and deterministic: no key can be recovered from the address, and a single changed input bit gives an unrelated output.

EIP-55: mixed-case checksum error detection

Take the lowercase 40-character hex address (no 0x), hash its ASCII text with Keccak-256, and look at the hash nibble at the same position as each address character. If the character is a letter (a–f) and its hash nibble is 8 or higher, it is written in uppercase; otherwise lowercase. Digits are unchanged. The address value is not altered, only its capitalisation, so old software that ignores case still works. A typo will almost certainly produce a case pattern that no longer matches.

4. Why several techniques and not one algorithm

Key management

BIP-39/32/44 let one backup phrase restore unlimited accounts in a predictable order. A hash or a curve alone cannot do that.

Public/private relationship

secp256k1 gives the one-way link between a secret and a shareable value, and the ability to sign. A hash function cannot sign.

Hashing

Keccak-256 shortens and fingerprints the public key. It is not reversible and has no algebraic structure to attack.

Error detection

EIP-55 protects users from typos. It does not add security against attackers, and secp256k1 or Keccak cannot do this job for humans typing text.

Each primitive has one role and is replaceable without breaking the others, which is the usual design principle in cryptographic systems.

5. Chronological context

  • 1977 RSA, the first widely used public-key system.
  • 2000–2001 secp256k1 is defined in SEC 2 (2000); SHA-2 including SHA-512 is standardised (2001).
  • 2012 BIP-32 (HD wallets); Keccak wins the NIST SHA-3 competition.
  • 2013 BIP-39 (mnemonic phrases).
  • 2014 BIP-44 (multi-account paths); Ethereum design is published.
  • 2015 SHA-3 standardised (FIPS 202); Ethereum launches.
  • 2016 EIP-55 (mixed-case checksum addresses).

The order matters: Bitcoin-era standards (BIP-32/39/44) were adopted by Ethereum wallets unchanged, and Ethereum only added Keccak-256 and EIP-55 on top.

NIST changed the padding of Keccak when standardising it as SHA-3, so SHA3-256 and Keccak-256 give different outputs for the same input. Ethereum had already adopted the original version, and its libraries call it keccak256. SHA-512 is used in the BIP-39/BIP-32 steps; Keccak-256 is used for addresses and EIP-55. SHA-2 and SHA-3 are unrelated in structure, so a break of one need not affect the other.

7. Statistical properties

  • Entropy is the only randomness. A 128-bit seed gives 2128 possibilities; 256 bits gives 2256. Everything downstream is deterministic and cannot add entropy, so weak initial randomness ruins the whole chain.
  • Uniform outputs. HMAC-SHA512 and Keccak-256 outputs look uniformly random: each bit is 0 or 1 with probability ½, and every hex digit appears with about 1/16 frequency.
  • Avalanche effect. Flipping one input bit flips about half the output bits (on average 128 of 256 for Keccak-256). Similar mnemonics give completely unrelated seeds and addresses.
  • Address space. 160 bits means 2160 addresses. By the birthday bound, an accidental collision between two addresses needs about 280 addresses, which is out of reach.
  • Mnemonic checksum. A 12-word phrase has 4 checksum bits, so a random wrong phrase passes with probability 1/16 (24 words: 8 bits, 1/256). It catches typos, not attackers.
  • EIP-55 strength. An address has on average 15 letters (40 × 6/16), each with a 50% chance of the right case by luck. A random error is therefore missed with probability about 2−15 ≈ 0.0247%. This is an approximate error-detection probability.
  • Work factor. PBKDF2 with 2048 rounds multiplies the cost of each brute-force guess on a weak phrase or passphrase by 2048. It does not rescue a low-entropy phrase.

8. Experiments to try

  1. Create a throwaway wallet in MetaMask, Rabby, Rainbow or Exodus and write down its 12 words. Never use a mnemonic that has held real funds.
  2. Import the same words into a second wallet and confirm both show the same first address (BIP-39/44 compatibility).
  3. Add a passphrase on import (where supported) and observe that the addresses change completely.
  4. Add accounts and compare the paths: …/0/0, …/0/1, …/0/2. Some wallets (e.g. Ledger Live style) vary the account level instead; note the difference.
  5. Take an address, change one letter's case, and paste it into a wallet that validates EIP-55; it should be rejected or warned about. An all-lowercase version carries no checksum and is accepted.
  6. Optional: in a script, compute Keccak-256 and SHA3-256 of the empty string and confirm they differ.
